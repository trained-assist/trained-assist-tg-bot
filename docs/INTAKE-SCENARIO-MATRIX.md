## Модель состояний (как есть в коде)

Каждый чат = один Durable Object `IntakeBuffer` с двумя состояниями:
- **idle** — всё пишется в `buf`, показывается одна плашка-накопитель с кнопкой «▶️ Запустить». Таймера нет.
- **busy** — идёт прогон: новые сообщения копятся молча, но подтверждаются плашкой «⏳ Принял ещё (N)». Кнопка ▶️ появляется снова только когда прогон закончился. Авто-запуска нет.

Запуск прогона — только явный: кнопка ▶️ ИЛИ голое force-слово (`запускай/запусти/поехали/го/go/run/начинай`).

### ✅ ЗАКРЫТО (было 🔴 ДЫРА №1) — медиа через накопитель доходит до агента файлом
Исправлено вариантом (B) из развилки ниже: файлы/голос теперь скачиваются и
транскрибируются НА ЭТАПЕ буферизации (`append`), а не в момент `_dispatch` строкой-тегом —
`_dispatch` отдаёт агенту настоящий контент. `tests/intake-media-content.test.js` (21 тест)
теперь зелёный целиком, включая control и буферный shape.
Историческая развилка (для контекста, решение уже принято и реализовано):
буфер физически нёс ОДНУ base-msg + склеенный текст, поэтому не мог пронести несколько файлов
за один запуск. Варианты были: (A) буфер хранит байты каждого файла, `_dispatch` передаёт
массив; (B) скачивать/транскрибировать в момент буферизации; (C) один файл + подпись, много
файлов запретить. Выбран (B).

### 🟡 ДЫРА №9 — новый диалог с файлом: пикер проекта не учитывает файл (сужено 2026-09-24)
Половина исходной дыры закрыта закрытием №1: файл в буфере больше не теряется (скачивается
при `append`). Оставшаяся половина: `handleMessage`/`getProjectDecision` решают показывать ли
пикер по тексту задачи (`msg.text || msg.caption`), без проверки наличия файла — так что файл
без подписи в новом диалоге ≥2 проектов всё ещё может упереться в пикер вместо прямого запуска.
Не потеря данных, просто лишний шаг. Теста на этот путь нет.

## 5. Главный концептуальный разрыв: разговор vs накопление

В idle-состоянии **любой** текст буферится — отдельного разговорного пути в idle НЕТ.
Единственный способ получить прямой ответ агента (не накопление) — **reply на сообщение
бота** (`shouldDebounce` → `msg.reply_to_message` → байпас). Это остаётся фактом: свежий
вопрос «ты умеешь X?» в idle всё ещё уходит в буфер, а не к агенту напрямую — это НЕ
переделывалось (владелец подтвердил 2026-09-15, что накопление как режим работы остаётся).

**Что было переделано (2026-09-15):** раньше «ответ» на буферизацию был ЭДИТОМ одного
и того же сообщения-коллектора/held-плашки — а правка старого сообщения невидима, если
чат уже проскроллен вниз (юзер продолжает печатать). Это читалось как «бот молчит после
моего сообщения», хотя формально подтверждение отправлялось. Юзер явно отверг это как
задокументированный, но плохой UX («я такого не говорил», «нужно явным образом ответить
на любое сообщение»). Фикс в `intake-buffer.js`: КАЖДОЕ сообщение (idle-накопление и
held-во-время-прогона) теперь получает СВЕЖИЙ bubble, `reply_to_message_id`-заякоренный
на само сообщение — не правку. Кнопка «▶️» у предыдущего коллектора снимается
(`editMessageReplyMarkup`), чтобы не копился хвост из активных кнопок; функционально это
косметика — любая кнопка флашит один и тот же буфер чата.
