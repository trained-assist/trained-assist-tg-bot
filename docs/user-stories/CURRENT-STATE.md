## Раздел A — Накопитель сообщений (`IntakeBuffer` Durable Object)

Модель: чат = один DO с состоянием `idle`/`busy`. idle: всё пишется в буфер,
показывается плашка-коллектор с кнопкой «▶️ Запустить проработку». busy: идёт
прогон, новые сообщения копятся молча с подтверждением «⏳ Принял ещё (N)».

### US-BUF-01: Юзер печатает несколько сообщений подряд, бот не занят

**Статус:** ✅ работает, покрыто (`tests/intake-buffer*.test.js`, C1/C2/C5 в матрице)

**Сценарий:**
1. Юзер: «первое сообщение»
2. Бот: свежий bubble-ответ, заякоренный (`reply_to_message_id`) на это сообщение, «Накапливаю (1)» + кнопка «▶️ Запустить проработку»
3. Юзер: «второе сообщение»
4. Бот: свежий bubble на ВТОРОЕ сообщение, «Накапливаю (2)» + кнопка; кнопка у ПЕРВОГО bubble снимается (`editMessageReplyMarkup([])`, `intake-buffer.js:325`), сам текст первого bubble не трогается
5. Юзер: жмёт ▶️ на любом из bubble
6. Бот: флашит весь буфер (оба сообщения) в одну задачу

### US-BUF-02: Юзер пишет, пока бот занят прогоном (busy)

**Статус:** ✅ работает, покрыто

**Сценарий:**
1. Юзер: запускает задачу (▶️ или force-слово)
2. Бот: начинает прогон
3. Юзер: пишет ещё сообщение, пока прогон идёт
4. Бот: «⏳ Иду по текущей задаче. Принял ещё (N) — покажу кнопку «▶️ Запустить», как закончу.» (`intake-buffer.js:53`)
5. Прогон завершается
6. Бот: показывает результат текущей задачи + отдельно всплывает кнопка ▶️ для held-сообщений

### US-BUF-03: Форс-слово вместо кнопки

**Статус:** ✅ работает, покрыто

**Сценарий:**
1. Юзер: «го» / «запускай» / «поехали» / «run»
2. Бот: немедленный запуск буфера, без ожидания клика по ▶️ (idle-состояние). В busy — слово игнорируется как флаш, сообщение просто копится held.

### US-BUF-04: Reply на сообщение бота — байпас буфера

**Статус:** ✅ работает, покрыто (C4)

**Сценарий:**
1. Юзер: делает Reply на любое сообщение бота с новым текстом
2. Бот: уходит СРАЗУ агенту, минуя накопитель — независимо от idle/busy

## Раздел B — Проект / сессия: с чем продолжает разговор бот

### US-PROJ-01: Новый диалог, 0 или 1 проект у профиля

**Статус:** ✅ работает, покрыто

**Сценарий:**
1. Юзер (профиль без проектов ИЛИ ровно с одним) пишет что угодно
2. Бот: автоматически использует единственный/дефолтный («Основной») проект, пикер не показывается

### US-PROJ-02: Новый диалог, ≥2 проекта — пикер

**Статус:** 🟡 предикат покрыт тестами, UX самого пикера (как выглядит, что происходит при истечении) — нет

**Сценарий:**
1. Юзер (профиль с ≥2 проектами) начинает новый диалог обычным текстом
2. Бот: показывает инлайн-пикер проектов (`pp:<idx>`), с кратким summary каждого проекта (генерируется на лету, `project-summary.js`, если есть `OPENROUTER_API_KEY`)
3. Юзер: жмёт нужный проект
4. Бот: создаёт/продолжает сессию в этом проекте, запускает задачу

**Открытый вопрос (см. `KNOWN-BUGS-2026-09-22.md`, US-BUG-01):** что происходит с ЭТИМ сообщением-пикером, когда юзер не нажал вовремя / выбор устарел — по факту остаётся видимым мёртвым сообщением в чате.

### US-PROJ-03: Слэш-команда — пикер никогда не показывается

**Статус:** ✅ работает, покрыто (`session-disambiguation`, merged 2026-09-18, commit `a7cc148`)

**Сценарий:**
1. Юзер (в любом состоянии, ≥2 проекта/сессии) шлёт `/hh_ats`, `/hh_scan` и т.п.
2. Бот: команда уходит сразу в last session, пикер проекта/сессии НЕ показывается

### US-PROJ-04: Quick-команды (engine-switch, info) — без привязки к проекту

**Статус:** ✅ логика есть (`/project-decision` в agent `server.js:1092-1104` возвращает `action:'quick'` сразу), 🟡 но нет мгновенного видимого ack на стороне бота — см. `KNOWN-BUGS-2026-09-22.md` US-BUG-05

**Сценарий:**
1. Юзер: `/switch2klod` (или `/switch2codex`, `/switch2opencode`, `/get_webpass` и т.п.)
2. Бот: пикер проекта пропускается полностью (регэксп `GLOBAL_QUICK_COMMAND`), команда обрабатывается как project-agnostic
3. Бот: подтверждает переключение движка текстом

**Фактическое поведение:** подтверждение — обычное текстовое сообщение без выраженного мгновенного статуса; наблюдалось в реальной сессии (22.09), что юзер отправил `/switch2klod` дважды подряд, получив на оба команды идентичный ответ — похоже на «не увидел мгновенной реакции → повторил команду», не на баг дублирования сервера.

### US-PROJ-05: Продолжение диалога (<2ч с последнего сообщения)

**Статус:** ✅ работает, покрыто

**Сценарий:**
1. Юзер писал в сессию < 2 часов назад
2. Юзер: пишет снова
3. Бот: тихо продолжает last session, без пикера и без вопросов

## Раздел C — Медиа (фото / голос / документ / видео)

### US-MEDIA-01: Голосовое сообщение доходит до агента как расшифровка

**Статус:** ✅ было 🔴 дырой №1 матрицы (медиа через буфер доходило как строка-тег `voice:<file_id>`, не как файл/текст) — **исправлено** commit `dc06ac7` «buffered media reaches agent as file, not a tag string (#66 gap, option B)». Проверить, что фикс пережил рефакторинги с 14.09 по 22.09 (последняя правка медиа — commit `7e8444e` widen media-retry backoff), но по логу это ортогональный ретрай-таймаут, не тот же путь кода.

**Сценарий:**
1. Юзер: присылает голосовое сообщение (idle ИЛИ во время накопления, любой момент)
2. Бот: буферизует; при флаше — расшифровывает голос В МОМЕНТ append (вариант B из матрицы), агент получает реальный текст расшифровки, а не тег

### US-MEDIA-02: Фото приходит, бот должен ПОНЯТЬ, что это фото (не голос)

**Статус:** 🟡 нужна повторная проверка вживую — конкретный кейс из жалобы владельца (см. `KNOWN-BUGS-2026-09-22.md` US-BUG-06): «я прислал картинку, бот написал «принял голосовую, расшифровываю»» — воспроизводилось ДО фикса дыры №1 (когда всё медиа схлопывалось в текстовый тег и типизация терялась по дороге); нужно перепроверить после `dc06ac7`, не осталась ли копия бага в тексте промежуточного ack-сообщения самого накопителя (bubble пишется ДО того, как тип файла разобран агентом).

**Сценарий:**
1. Юзер: присылает фотографию
2. Бот: bubble-ack должен отражать реальный тип вложения («📷 принял фото», не «🎤 принял голосовое») на каждом шаге — и в accumulate-ack, и в agent-side обработке

### US-MEDIA-03: Видео

**Статус:** 🟠 матрица отмечала «буфер принимает, `handleMessage` не умел видео» — есть коммит `7e8444e` widen media-retry backoff «to survive a VM restart blip», это про надёжность доставки, не про поддержку видео как типа. Требует отдельной проверки: видео сейчас реально доходит до агента как контент или всё ещё как тег/заглушка.

### US-MEDIA-04: Документ

**Статус:** ✅ считается закрытой тем же фиксом `dc06ac7` (вариант B применялся ко всем типам медиа единообразно) — не выделялась отдельно в коммитах, надо подтвердить тестом, специфичным для документа.
